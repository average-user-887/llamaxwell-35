DECISION AND EXACT FLAGS

Use the existing isolated routing-stack profile and keep all target-model,
offload, context, batch, cache, sampling and performance options identical.
No new model, draft weights, downloads, CPU inference or GPU ownership changes.

Arm A:
  --spec-type none

Arm B:
  --spec-type ngram-simple --spec-ngram-simple-size-n 4 --spec-ngram-simple-size-m 8

This uses exact token-history matching and proposes at most eight tokens from
the same request's history. CPU token lookup is not CPU model inference.
Do not add draft-model/HuggingFace flags. Do not set synthetic-acceptance flags
or LLAMA_ARG_SPEC_SYNTH_LEN / LLAMA_ARG_SPEC_SYNTH_RATES environment variables.
Those synthetic options replace target verification and cannot establish quality.

The actual production-app CLI supports these flags; see production-cli-help.txt.
The old --draft/--draft-max options are explicitly removed in this binary.
--spec-draft-n-max does NOT bound ngram-simple: use its own size-m option.
Do not set size-m below size-n: the simple implementation then returns no draft
because copy_max < n_draft_min. The simple mode ignores its exposed min-hits
setting; its actual config contains only n-gram and m-gram lengths.

A small optional second step, only if B has substantial acceptance, is size-m=4
versus8 to measure verification/checkpoint economics. This is not a mandatory
full sweep. Avoid48-token default drafts during the first bounded experiment.

ACCEPTANCE AND METRICS

Require live /slots or equivalent configuration evidence that B has speculation
enabled and A does not. A valid response alone is insufficient: initialization
can catch a speculative exception and continue with spec=nullptr; no-match mode
can also produce ordinary decoding with zero drafted tokens.

Retain complete response text/token counts, client monotonic wall time, prompt
time, prediction time, draft_n and draft_n_accepted when present, and startup/
request logs. Server metrics expose spec_decode_num_draft_tokens_total,
spec_decode_num_accepted_tokens_total and spec_decode_num_drafts_total. The log
prints draft acceptance and mean accepted length when actual drafts exist.
Use metric deltas for the isolated run, not cumulative totals from unrelated work.

Compare committed output tokens per elapsed second, completion wall time and
task correctness. Acceptance alone is not a win; it can hide expensive verification
or replay. Compare exact greedy A/B token/output sequences and independently check
semantics. Batch-shape numerical differences mean sample-and-match does not prove
bit-identical output versus one-token decoding in this custom stack.

Leave trace logging off during scored timing. If diagnostics are required, a
single separate LLAMA_TRACE=1 run exposes accepted counts/checkpoint restore lines;
do not compare that instrumented request directly against uninstrumented A.

ROLLBACK, MEMORY AND KERNEL CAVEATS

The configured ngram modes do not request recurrent rollback slots:
common/common.h:399-405 need_n_rs_seq() returns draft.n_max only for MTP/Eagle3/
DFlash/DSpark, otherwise0; common/common.cpp:1712 uses that result.

The server probes the target context's sequence-removal ability. Without bounded
rollback, the hybrid recurrent model normally uses checkpoint-based rollback.
For every nonempty draft it saves target partial state; on a rejected suffix it
restores that checkpoint, restores the sampler, and replays the accepted prefix.
These costs are part of the real experiment and must not be subtracted away.

Partial state here is NOT the full long-context attention KV cache:
src/llama-memory-hybrid.cpp:190-205 skips attention serialization when
LLAMA_STATE_SEQ_FLAGS_PARTIAL_ONLY is set, but saves/restores recurrent state.
common/common.cpp:2381-2430 stores it in a host vector via the state API.
No extra model weights are needed. There is still host checkpoint storage,
GPU/host state transfer, more simultaneous logits and target verification scratch.
The current pilot has not measured these byte counts or transfer costs.

The fast custom Occamy attention applicability guard requires Q->ne[1]==1
(ggml/src/ggml-cuda/fattn-occamy.cu:621). An8-token proposal verifies up to9 query
positions, so it does not use that single-query kernel. This pilot therefore tests
the actual existing generic verification path, not a future tiny-batch kernel.

QUALITY SEMANTICS

For ngram-simple the drafter emits no probability distribution. Target verification
falls back to common_sampler_sample_and_accept_n(): sample the target at each
position, accept only matching proposals, stop at the first mismatch, and append
one extra target token if all proposals match. This is not unchecked acceptance.
Temperature0 makes the intended check greedy; runtime numerical/kernel behavior
and recurrent replay still need the actual output comparison described above.

Avoid ngram-mod as the first test: its defaults are48-64 proposal tokens and its
source explicitly warns about lookup lengths below16. ngram-cache uses a fixed
eight-token proposal limit plus optional cache-file state. ngram-map-k/map-k4v
add per-sequence lookup tables and more lifecycle state. These may be useful later,
but ngram-simple has the smallest state surface for this first real sample.
