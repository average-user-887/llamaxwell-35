# Row-major task placement for the two-row MoE cohort

This candidate changes the mapping from physical CUDA block coordinates to logical work. For the existing 24×2 grid the original chooses the row by alternating flattened block IDs and the local tile by dividing the flattened ID by two. The candidate uses the grid's Y coordinate as the row and X as the local tile. Each row still has all its 24 tiles, its original scratch/barriers, and the same weights, full eight-expert order, shared expert and FP32 arithmetic. The retained 369c6b05 CUDA library relinks exactly and all 17 original device functions, 46,032 machine instruction and scheduling words, are identical. The row-major candidate starts from that parent. Both timed kernels omit the SM-ID instruction. The model server identity is 4a0ff82d.

GGML_CUDA_OCCAMY_MOE_Q2_LAYOUT=1 selects row-major layout only after the original fixed-shape two-row cohort and separate kernel residency check admit it. Otherwise the existing cohort runs. A dedicated issued-kernel counter and the original paired launch, skipped second callback and fallback counts distinguish the physical paths. Production defaults use the original layout. The candidate uses 64 registers, the control 63, both with 96 static and 39,424 dynamic shared bytes and no spills. The dimensions, two 512-thread blocks per SM on 24 SMs, are verified in the running process.

The physical diagnostic uses the untapped original and candidate for the two exact 4,096-word output and ordered top-eight route comparisons with a candidate repeat. It then makes two separate mapping captures per fixture per layout using diagnostic kernel variants. Thread zero in each CTA reads the PTX SM ID and writes physical x/y, row, local tile and SM to its private region of the row's unused router scratch. Before each capture the observer fills the records with a sentinel. It checks the 48 distinct tuples, grid coverage, row/tile mapping, two blocks per observed SM, and exact outputs and routes of every tapped replay. The complete 384 records and derived co-resident row and tile counts are in the portable receipt. These samples directly describe diagnostic variants only. The timed kernels collect no placement observations.

The same graph and candidate library are used in both timed modes, with route readbacks and placement disabled. Independent routes use A/B/B/A and five-common routes B/A/A/B, following two warmups with four batches of 96 synchronized calls per fixture. The sole materiality threshold is 18 microseconds/layer saved in all four paired intervals. At full model transfer that would represent 0.72 milliseconds across 40 layers. Real throughput requires separate measurement. The operator measures neither model output quality nor per-token time.

Run bash build.sh, python3 -B prepare-host.py, bash build-host.sh and python3 -B verify-build.py for CPU-only compilation and build verification. The fixed runtime dependencies are listed in INPUTS.sha256 and RUNTIME.sha256. Run ./release.sh --check for the frozen preflight. The sole GPU owner may run N3_GPU=<admitted device> ./release.sh --run under the existing Fleetdash admission, exclusive lock and shared 180-second cap.
