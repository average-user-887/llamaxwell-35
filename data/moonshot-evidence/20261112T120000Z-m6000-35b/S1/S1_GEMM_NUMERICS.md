# S1 GEMM vs stock-tile numerics (read-only, CPU). 12 Nov 2026
G = integration-v4/src/ggml/src/ggml-cuda/fattn-maxwell-gemm.cuh (file line = patch line - 28). T = fattn-tile.cuh, C = fattn-common.cuh.

## 1. Departures from the stock path
- Premise fix: on sm52 FAST_FP16_AVAILABLE is off (common.cuh:267-272, Pascal+ only), so the stock tile path is also FP32 math (Q float, K/V F16 storage only). Both arms read identical F16 K/V. Build is -use_fast_math, so expf ~ __expf in both.
- KQ: stock = per-thread FP32 FMA dot over D in nbatch_K slices, 256-key tiles (T:624-630). GEMM = cublasSgemm FP32, K converted F16->F32 (G:19-30, 242-246); cuBLAS summation order unknown.
- Scale: stock multiplies Q by scale in FP32 before use (T:939). GEMM applies scale as SGEMM alpha (G:243). Scale is 0.0625 = 2^-4, exact either way. No cast/rounding difference.
- Softcap/ALiBi/sinks: stock supports them (T:648); GEMM rejects them in the guard (G:189-191), so no difference on engaged shapes.
- Mask: both add the F16 mask in FP32 after scaling (T:654 vs G:94,113). -inf handled safely in both: GEMM max starts at -FLT_MAX (G:91), row of all -inf gives total 0 -> zeros (G:105-110). Stock gives nonfinite for an all-masked row (GPU_RESULTS). No causal logic in GEMM; it trusts the mask tensor only. Padded queries are zeroed (G:84-89, 35-47) and not written (G:139).
- n_kv padding: llama pads n_kv to 256 (llama-kv-cache.cpp:1285), key_count = K->ne[1] (G:193). Padded keys are masked -inf, contribute exactly 0 in softmax. Stock skips fully masked 256-tiles only when Q>=1024 and n_kv%256==0 (C:1157, T:968); GEMM never skips, so garbage/NaN in padded K/V rows would poison it (0*NaN). Runs show no NaN.
- Softmax: stock = online per-tile, max shifted by FATTN_KQ_MAX_OFFSET (+2.08, C:21, T:656), running rescale of sum and VKQ (T:689-712), single divide by KQ_sum at the end (T:1108). GEMM = per-thread online max/sum, then block reduce (G:50-75, 91-101), recompute exp with true max (G:113), normalise P BEFORE PV (inverse_sum). Same maths, different rounding. Exact max subtraction, no offset.
- V accumulation: stock FP32 running accumulate with rescale. GEMM: P (normalised, FP32) x V (F32) in 4096-key split SGEMMs (batched G:252-255, tail G:259-263), partials summed in order in FP32 (G:129-147). Different order, same precision.
- GQA map: head = group*8 + local_col/64 (G:44), group = kv head 0/1 (G:241,262). Matches h / (16/2). Output index (q*16+head)*256+d (G:146) matches dst layout. Looks correct.

## 2. Bug suspects, ranked
1. (Coverage gap, not a found bug) key_count that is an exact multiple of 4096 => tail_keys=0 (G:196-198), only the batched PV path runs. Operator tests used K=98048 (tail 3840) and 4352 (tail 256) only. The 16K and 65K quality rows both come from a bulk ubatch ending at n_kv=16384 and 65536 (cached 65532 -> pad 65536; server.log lines 1099-1103), i.e. tail=0. 32K (pad 33024, tail 256) and 98K (tail 3840) show KL 2e-4 and 6e-6; 16K and 65K show 7e-3 and 0.29. Four points, could be coincidence. Code read of the tail=0 branch finds no fault.
2. int overflow: none found. Index math uses size_t (G:22,35,83,100); max score elements 98304*512 = 50M < 2^31; split pointer index*4096 tiny. 2^16 itself is not special in code (grid 65535 is grid-stride, G:263).
3. Chunk/ubatch boundaries, off-by-one keys: key range is always 0..key_count-1 against the mask row, mask->ne[0]>=key_count and ne[1]>=n_q are guarded (G:179-180). No sequence boundary (ne[3]==1 forced). Nothing found.
4. NaN/garbage in padded KV rows (see mask bullet): low.

## 3. Verdict on the 65,536 outlier: undetermined, leaning "propagated sensitivity, not a direct kernel bug"
- Key fact: the scored position is NOT computed by the GEMM kernel. Row at 65536 is a 4-token tail then 1-token appends (server.log 1103, 1124: cached 65536, +1), below the 64-query guard, so both arms run the stock kernel there. The difference comes only from KV/recurrent state built earlier by GEMM ubatches. That is accumulated drift through 40 layers, GDN state and quantised activations, which fits the "dense in 16K/65K, tiny in 98K" pattern of a low-margin position (teacher is non-top1, ' loss' vs ' accuracy').
- For FP32 being "more accurate": operator RMSE vs FP64 is lower for GEMM (7.2e-9 vs 2.8e-8, closer 90/112) on synthetic data. NLL gain 2.648 -> 1.901 on one token is one sample; mean signed NLL over 16 rows at 65K is -0.048, other checkpoints are +0.02/+0.003/+0.002. Not enough to call it better.
- Cannot rule out a tail=0 bug (suspect 1) from reading alone.
- Cheapest separating GPU test: rerun the 65K window (stock arm vs GEMM arm) with a third arm = stock with a benign reorder (e.g. GGML_CUDA_FA_PARALLEL_BLOCKS_MULT=2 or a tune variant; ubatch 512 was already bit-exact so use a variant that changes tile order), and a fourth arm = GEMM with the bulk ubatch forced to key_count != multiple of 4096 (e.g. prefix shifted by +300 tokens). If stock-vs-stock-variant KL is also large, it is chaotic sensitivity. If only the exact-multiple arms drift, bug in tail=0. A true high-precision reference needs FP64 attention, not available cheaply on GPU.

## 4. Engagement guard (G:154-191, dispatched first in ggml_cuda_flash_attn_ext)
Env GGML_CUDA_FA_MAXWELL_GEMM=="1" (cached at first call); device cc==520; Q F32, K F16, V F16, dst F32 contiguous; no sinks (src[4]); D=256 for Q/K/V/dst; Q heads 16, KV heads 2; ne[3]==1; Q count 64..1024; K count 4096..98304, V count == K count; dst ne=[256,16,nQ,1]; byte strides: nb0 exactly 4/2/2, other strides divisible by element size; mask optional but if present F16, ne[0]>=K, ne[1]>=nQ, ne[2]==ne[3]==1, nb0==2, nb1%2==0; scale finite, max_bias==0, softcap==0, op_param[4] (sparse n_kv_max)==0. Else falls through to Occamy/stock. Q<64 (decode, short tails) and K<4096 or >98304 use stock.
